# UI interaction audit

Source review on November 14, 2026, in the creator budget integration worktree. This is a control and state audit of `apps/web/src` and the public showcase, using the existing product brief and Impeccable audit/product guidance. No browser, screenshot, viewport, live provider, or assistive technology testing was performed. Visual contrast, clipping, actual target sizes and rendered focus order remain unverified; a visual health score would imply checks that were not performed.

Follow-up on November 15, 2026: the new script project form (`#/new`) now uses actionable field errors and focuses its first invalid input after submission. Actual Chrome checks at 1365×900 and 390×844 verified empty submission, then successive correction of the project name and idea, with preserved values and valid error-description links. These checks do not establish assistive-technology or live-provider coverage for the other inventory items.

The main task remains: supply an idea and photos, refine a proposal, explicitly review production cost, then download a real film and caption. Decorative artwork and progress labels do not need click handlers. Controls that claim to save, share, approve or copy must complete that action or offer a usable recovery.

## Initial findings and resolutions

### P0: Creator production controls do not yet implement the quote contract

- **Evidence:** [useCreatorSession.ts](../apps/web/src/creator/useCreatorSession.ts), `approveAndProduce`, lines 620–695; [creator/api.ts](../apps/web/src/creator/api.ts), lines 160–168; [CreatorWorkspace.tsx](../apps/web/src/creator/CreatorWorkspace.tsx), `ProductionReview`, lines 1411–1549.
- **Behavior:** The reviewed baseline sends approval without `quoteId`/`costReviewed`, and production without `quoteId`. It has no quote request or dollar budget review. The integrated server now requires these fields, so the primary paid generation action cannot complete. The existing retry path also retains an old approval, while each new paid attempt now needs a fresh quote and approval.
- **Owner:** Bonefish creator owner. This is a known integration task, not a request for the shell owner to edit creator files.
- **Fix:** Display the server quote, expiry and remaining app budget; require explicit cost review; pass its ID through approval and production; request a fresh quote for manual retries. Preserve unknown-outcome request IDs and existing job reconnect behavior.

### P1: Creator model and duration controls contradict the selected provider

- **Evidence:** [CreatorWorkspace.tsx](../apps/web/src/creator/CreatorWorkspace.tsx), `ShotInspector` around line 1280 (`min={2}`), and `ProductionReview` around line 1460 (`Runway Gen 4.5`).
- **Behavior:** Default production is now FAL Seedance, with a four-second minimum. The editor accepts two- and three-second clips and displays Runway as the model. The backend later refuses an unsupported duration at quote time, after the user has saved it.
- **Owner:** Bonefish creator owner.
- **Fix:** Derive the displayed provider/model and duration constraints from the production profile/capabilities. Explain the valid range next to the field and validate before save/quote. Update the former two-attempt approval language to distinguish the plan limit from the one-attempt cost quote.

### P1: Photo promo caption copy can throw before its fallback

- **Evidence:** [PromoWorkspace.tsx](../apps/web/src/promo/PromoWorkspace.tsx), lines 1864–1880.
- **Behavior:** `navigator.clipboard.writeText(...).then(...).catch(...)` dereferences `clipboard` before a promise exists. In a context without the Clipboard API, clicking Copy caption throws synchronously and never announces the manual-copy alternative.
- **Owner:** Unified shell/photo promo owner.
- **Fix:** Check capability or use `try/await/catch`. On failure focus/select the existing read-only caption and announce that it can be copied manually. The legacy project copy handler already catches synchronous access correctly.

### P2: Landing Save and Like do not belong to the selected reel

**Resolution prepared:** The landing actions change now persists bounded per-source saved/liked IDs, restores them on reload and refreshes button state and labels for the displayed reference. Failed browser storage leaves explicit visit-only behavior. Pure storage/identity tests pass; rendered browser verification remains unperformed.

- **Evidence:** [public/app.js](../public/app.js), `updateReel` around line 481 and `[data-toggle]` handler around line 637.
- **Behavior:** Both actions only toggle the shared phone button's `aria-pressed` state and show a toast. Changing reels inherits the previous reel's saved/liked appearance. No reel IDs are retained, and there is no saved result to recover after a reload.
- **Owner:** Assigned landing actions owner.
- **Fix:** Store bounded stable reel IDs, update state on every selection, recover safely from unavailable/corrupt storage, and provide truthful saved/removed feedback. Keep these personal preferences separate from public engagement metrics.

### P2: Share this reel loses the selected reel and has no usable copy fallback

**Resolution prepared:** Links now encode a stable source ID, use the outer app URL when embedded and restore the exact reference even on a narrow wall. Clipboard failure opens a labeled native dialog containing the selectable link. Helper, source-wiring and existing gallery/motion checks pass; no browser verification is claimed.

- **Evidence:** [public/app.js](../public/app.js), `share-reel` handler around line 659.
- **Behavior:** The copied link contains only `#reels`, so it opens the general showcase instead of the selected entry. Clipboard failure shows a toast but does not expose a selectable link. Embedded and standalone destinations must also be distinguished.
- **Owner:** Assigned landing actions owner.
- **Fix:** Encode a stable selected reel ID, restore it at load, and construct an outer-app URL when embedded. On clipboard failure offer a visible labeled, selectable link or the native share sheet.

### P2: Legacy project tabs lack the expected keyboard behavior

- **Evidence:** [ProjectEditor.tsx](../apps/web/src/ProjectEditor.tsx), `editor-tabs` around lines 405–438.
- **Behavior:** Script, Shot plan and The brief declare `role="tab"` but all remain in the Tab order and have no Arrow/Home/End handler. Keyboard activation works as ordinary buttons, but the announced tab interaction does not match the creator and research tabs.
- **Owner:** Unified shell/legacy project owner.
- **Fix:** Use a roving tab stop with ArrowLeft/Right/Home/End selection and focus, or remove tab semantics and expose an ordinary button group. Preserve the existing panel IDs/labels.

### P2: Reference-room empty filtering offers no direct reset

- **Evidence:** [ReferenceBoard.tsx](../apps/web/src/creator/ReferenceBoard.tsx), filtered results around lines 137–146 and the result list through the final Explore more films action.
- **Behavior:** An unmatched search/category renders a zero count and an empty grid. There is no clear-search/reset action or explanation of how to recover; users must manually edit the query and category.
- **Owner:** Bonefish creator owner.
- **Fix:** Add an inline empty result message with a Clear filters button resetting query, category and pagination. The standalone film room and photo promo library already use this recovery pattern.

## Cross-cutting conclusions

- Source-level form labels are present for the inspected entry, interview, promo, research, search and shot controls; no unlabeled visible form control was identified. Generated icon controls generally provide explicit accessible names.
- Main app, creator, research and film-room styles contain focus-visible rules, disabled states and reduced-motion overrides. Their rendered contrast and target sizes are not verified by this report.
- Shared navigation, genuine save/download handlers, explicit destructive confirmations, version conflict recovery, safe external citations and real job polling are strengths to preserve.
- Quote integration, clipboard recovery, personal actions, keyboard navigation and filter recovery are implemented and checked at source/HTTP level. Browser verification remains unperformed under the user's explicit no-computer-use instruction.
