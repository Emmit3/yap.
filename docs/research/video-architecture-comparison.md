# Video backend architecture comparison

Checked November 14, 2026. This compares Yap's implemented backend at [`055358aaafe1f878cd96af2ea516f2a36d931ea8`](https://github.com/Emmit3/yap./commit/055358aaafe1f878cd96af2ea516f2a36d931ea8) with four first-party codebases and their official documentation. Sources were found and read with Firecrawl; exact repository revisions were resolved through the public GitHub API and selected source files read directly. No other project was installed or benchmarked, and no paid generation was performed.

The useful distinction is between **generating footage**, **composing/encoding existing media**, and **running a creator product**. A rendering library does not itself supply a business interview, factual review, generation budget or publishing permission. These projects cover different layers, so this is not a feature leaderboard.

## What each architecture actually contributes

### Remotion: separate render identity from the HTTP request

Remotion Lambda deploys a composition website and renders frame ranges using Lambda functions. The current detailed implementation streams chunk data and progress back to a coordinating function, which maintains `progress.json` and uploads the completed video to S3. The high-level overview still mentions intermediate S3 chunks; the more specific lifecycle describes the newer streaming path. This matters when estimating storage and network work. [Detailed lifecycle](https://www.remotion.dev/docs/lambda/how-lambda-works).

`renderMediaOnLambda()` returns a render ID and bucket identity. Progress can be queried separately, including fatal errors, frame/chunk counts, output information and cost estimates. It supports signed private output and completion/error webhooks. Its retry setting concerns rendering chunks for a bounded set of flaky failures; it is not permission to regenerate paid model footage. These are concrete operational patterns Yap can learn from without adopting AWS for a small local experiment. [Render options](https://www.remotion.dev/docs/lambda/rendermediaonlambda), [progress contract](https://www.remotion.dev/docs/lambda/getrenderprogress).

### Revideo: one scene definition for preview and export

Revideo's headless renderer accepts a TypeScript project and dynamic variables, while its React player previews that project. The inspected renderer launches browser/server workers, reports worker progress, collects their audio/video outputs, concatenates them and cleans temporary files. Its `workers` setting scales composition work; it does not define durable product jobs or a shared generation ledger. Those higher-level behaviors were not established by the inspected renderer, rather than assumed absent everywhere in the ecosystem. [Project capabilities](https://github.com/midrender/revideo/blob/b5de67a009a55aa2768a1e178b0446b2479a0b4e/README.md), [renderer source](https://github.com/midrender/revideo/blob/b5de67a009a55aa2768a1e178b0446b2479a0b4e/packages/renderer/server/render-video.ts).

The architectural lesson is preview/export agreement. A promotional film's text layout, crop, animation and timing should derive from one validated composition description. This is independent of whether footage comes from a camera, a creator photo or Seedance.

### MoneyPrinterTurbo: durable admission and incremental revisions

The API selects an in-memory or Redis task manager. Redis task state uses hashes, and queue admission/claim operations use atomic scripts. Running slots have renewable leases, queued work can be dispatched after startup, and queue capacity is bounded. These are mechanisms for multi-process task admission that Yap's current process-local worker does not provide. They do not establish exactly-once billing by an external model provider. [API admission](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/app/controllers/v1/video.py), [Redis manager](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/app/controllers/manager/redis_manager.py), [task state](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/app/services/state.py).

Its separate local video-project path is especially relevant to a small business revising a promo. It snapshots prepared media, retains immutable revisions and reuses completed stages when dependency fingerprints and artifact hashes match. Changing a scene rebuilds affected stages; changing only background music rebuilds the final mix. Failed or interrupted local rendering requires an explicit retry. An older revision cannot replace a newer current export. The guide explicitly separates this local renderer from provider generation and makes no paid-generation idempotency guarantee. [Revision and artifact contract](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/docs/video-projects.md).

The broader pipeline includes narration, subtitles and background music, whereas Yap's current generated production is silent. Those are separate product capabilities with their own media rights, user approval and potential API costs, rather than automatic benefits of switching renderers. [Audio/subtitle capabilities](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/README-en.md#voiceover-subtitles-and-background-music-%EF%B8%8F).

### OpenCut Classic: local editing and explicit export events

Classic's local storage adapter uses IndexedDB transactions. Its `SceneExporter` renders a scene frame by frame to a canvas, encodes through Mediabunny, emits progress/completion/error/cancellation events, and checks cancellation during export. It returns media bytes locally; this export component is not a cloud paid-generation queue. The code also supports audio export, which is distinct from Yap's silent output. [Storage adapter](https://github.com/OpenCut-app/opencut-classic/blob/cf5e79e919144200294fb9fed22a222592a0aeea/apps/web/src/services/storage/indexeddb-adapter.ts), [exporter](https://github.com/OpenCut-app/opencut-classic/blob/cf5e79e919144200294fb9fed22a222592a0aeea/apps/web/src/services/renderer/scene-exporter.ts).

This illustrates a useful privacy and responsiveness option for later editing: local preview/export can avoid uploading every adjustment. It does not remove the need for server-side ownership checks when a product also generates paid remote footage. Shared multiplayer editing was not established by the inspected local storage/export files.

Our mocked adapters and fixture renders establish application behavior; they do not measure live model quality, latency or actual billing.

## Justified next improvements

These are recommendations, not delivered functionality or authorization to spend.

1. **Recover known remote tasks without another paid POST.** Retain the conservative restart behavior, then add an explicit reconciliation operation using the already saved provider task ID. It should query only allowlisted status/result endpoints, import a completed result after checks, and release cost holds only on authoritative billing evidence. A completed old task must not become a current approved export automatically. Remotion's separate render ID/progress lifecycle demonstrates the value of status independent of submission. Acceptance: crash after submission, reconnect and retrieve the same task with zero new generation POSTs. [Progress pattern](https://www.remotion.dev/docs/lambda/getrenderprogress), [Yap current restart behavior](https://github.com/Emmit3/yap./blob/055358aaafe1f878cd96af2ea516f2a36d931ea8/apps/api/src/creator-repository.ts).

2. **Reuse unchanged clips across revisions with explicit dependency hashes.** Current Yap reuse is scoped to the same plan; saving a changed caption creates a new plan identity. Add a project-scoped artifact record keyed by exact source hashes, clip direction, provider/model, generation parameters and audit policy version. A caption-only edit should require fresh publish approval while buying no new footage. A changed clip prompt must not reuse the old generated clip. Include normalization/encoder versions in downstream transformation fingerprints, and preserve the last successful export as historical material. MoneyPrinterTurbo's prepared-media revision design supplies a concrete reference for this boundary. Acceptance: caption-only change makes zero paid calls; one changed shot regenerates only that shot after a new exact quote. [Yap plan save](https://github.com/Emmit3/yap./blob/055358aaafe1f878cd96af2ea516f2a36d931ea8/apps/api/src/creator-router.ts), [revision reference](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/docs/video-projects.md).

3. **Use one validated composition description for preview and final assembly.** Keep expensive footage generation separate from cheap text, logo, crop and timing revisions. Define a serializable composition with approved media IDs, timings, brand typography, text safe areas and animation choices, then have preview and encoding consume it. Revideo's shared player/project and OpenCut's explicit scene export show this seam. This need not start with a renderer migration. Acceptance: fixture frames verify the same crop, text placement and timing at preview/export boundaries; an overlay change does not silently call the video model. [Revideo player/project contract](https://github.com/midrender/revideo/blob/b5de67a009a55aa2768a1e178b0446b2479a0b4e/README.md), [OpenCut scene export](https://github.com/OpenCut-app/opencut-classic/blob/cf5e79e919144200294fb9fed22a222592a0aeea/apps/web/src/services/renderer/scene-exporter.ts).

4. **Add transactional storage and leased workers when shared hosting is needed.** Move admission, quote consumption, reservations and job ownership into database transactions with unique idempotency keys before starting multiple API processes. Workers need ownership leases and fencing so a stalled old worker cannot publish after a replacement takes over. MoneyPrinterTurbo demonstrates atomic admission and expiring running slots; Yap still needs its own billing/approval invariants preserved through such a change. Acceptance: two competing processes cannot spend the same quote or exceed one app budget. Defer cloud render fan-out until workload measurements justify its operational cost. [Redis admission/lease example](https://github.com/harry0703/MoneyPrinterTurbo/blob/ce289ffb61a118779c56d6b4a34181905dbed2b9/app/controllers/manager/redis_manager.py).

For the current USD 35 experiment, reconciliation and revision reuse have the most direct relationship to avoiding waste. Keep one paid worker, preserve manual cost approval, test with local fixtures, and spend a small approved live test on actual product fidelity before buying concurrency or adding another provider. That prioritization is an engineering inference from the inspected architectures, not a measured savings claim.
